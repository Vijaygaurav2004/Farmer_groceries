Abstract

The Indian agricultural supply chain routinely places five or more intermediaries between the grower and the household that eventually consumes the produce. Each intermediary adds margin without adding value, with the result that farmers realise only a fraction of the final retail price while consumers pay a substantial mark-up, and perishable produce loses freshness at every additional hop. Farmer Groceries is a cross-platform mobile application that compresses this chain to a single link — farmer to delivery partner to consumer — inside one application serving three distinct user roles.

The implemented system is a React Native application built on the Expo SDK 54 managed workflow, written entirely in TypeScript under strict compiler settings and routed with the file-based Expo Router. A single authenticated identity is specialised at sign-in time into one of three role workspaces: customers browse a categorised catalogue, manage a persistent cart and track orders through a seven-stage progress timeline; farmers publish and price inventory, monitor low-stock alerts and advance incoming orders; delivery partners receive nearby jobs with distance-derived ETAs, accept or decline them, follow a pickup-to-drop route view and monitor period-wise earnings. Global state is held in React Context providers for authentication and cart, while all persistence is funnelled through a single service façade that dispatches either to a Supabase (PostgreSQL + Auth + Storage) backend or, when no cloud credentials are configured, to an on-device data layer persisted through AsyncStorage. This dual-target design makes the application offline-capable — every screen continues to function without connectivity — while remaining ready for multi-tenant cloud deployment.

The delivered build comprises 48 TypeScript source files (approximately 5,400 lines) spanning 18 routed screens and a 12-component reusable design system driven by a central token module. The application compiles cleanly under tsc --noEmit in strict mode and was validated by automated end-to-end suites, committed to the repository, that drive all three role workflows through a real browser — covering sign-in, role selection, catalogue browsing, cart and checkout, order placement, farmer-side fulfilment and delivery acceptance through to completion. Forty functional and validation test cases were executed, of which all forty passed. The outcome is a working, demonstrable marketplace that measurably shortens the produce supply chain and provides a credible foundation for a production deployment.

Chapter 1: Introduction

Note: Problem identification and system design were completed and approved as part of the preceding Study Project. This chapter reproduces that work in condensed form and records the refinements made during implementation. The principal changes are: (i) the adoption of Supabase in place of the originally proposed Firebase backend, (ii) the addition of an on-device data layer so that the application remains fully functional without network connectivity, and (iii) the extension of the order lifecycle from five to seven states to give delivery partners explicit assigned and picked up checkpoints.

1.1 Overview of the Project

Farmer Groceries is a cross-platform mobile marketplace that connects agricultural producers directly with the households that buy their produce, and coordinates the last-mile delivery between them. The application is built as a single React Native codebase that runs on Android, iOS and the web, and it serves three distinct classes of user from that one codebase. A person signs up once, chooses a role, and is thereafter routed into a workspace tailored to that role: a shopping experience for customers, an inventory and fulfilment console for farmers, and a job board with route and earnings tracking for delivery partners.

The commercial premise of the system is disintermediation. Every order placed in the application creates a direct commercial relationship between one farmer and one customer, with a delivery partner compensated separately for the physical movement of goods. There is no wholesaler, commission agent or retailer in the transaction path, so the margin those parties would otherwise extract is redistributed between the producer and the consumer.

The delivered artefact is a complete, runnable application rather than a prototype of selected screens. All eighteen routed screens are implemented and reachable, the order lifecycle can be driven from placement to delivery by three different users acting in sequence, and state changes made by one role are immediately visible to the others. The system persists data through a service layer that can be pointed either at a hosted Supabase project or at the on-device data layer, so the application keeps working whether or not the network does.

1.2 Problem Statement and Motivation

Produce in the conventional Indian agricultural supply chain typically passes through five or more intermediaries between the field and the kitchen. A grower sells to a local trader or an aggregator, who sells to a commission agent operating in a regulated wholesale market, who sells to a wholesaler, who sells to a retailer, who finally sells to the household. Each hop adds a margin, a handling delay and an opportunity for spoilage, and none of the hops after the first adds any agronomic value to the product.

Three consequences follow directly from this structure, and together they constitute the problem this project addresses:

  • Producer income is compressed. The share of the final retail price that reaches the grower is a small fraction of what the consumer pays, because each intermediate party prices for its own risk and working capital rather than for value added.
  • Consumer prices are inflated. The household pays for a chain of margins it never interacts with, and has no visibility into who grew the produce, when it was harvested, or under what conditions.
  • Freshness and quantity are lost. Perishables spend days in transit and storage across the chain. Wastage accumulates at every transfer, and what survives arrives materially less fresh than it left the farm.

The structural fix is to shorten the chain, and the practical obstacle to shortening it is coordination. A farmer cannot economically discover, price for, and deliver to individual households without software; a household cannot discover nearby farmers or verify their produce without a catalogue; and neither party can arrange reliable last-mile logistics alone. A single application that carries all three participants and mediates the transaction between them removes that coordination barrier. Figure 1.1 contrasts the two structures.

Chapter 2: Implementation Details

2.1 System Architecture and Design

2.1.1 High-Level Architecture

The application is organised into five layers with a strict downward dependency rule: a layer may import from the layers beneath it but never from those above. This constraint is what makes the backend substitutable — screens never import a database client, they import a service, and the service decides where the data comes from.

The presentation layer consists of eighteen routed screens declared as files under app/. Expo Router derives the navigation graph from the directory structure, so the three parenthesised directories (customer), (farmer) and (delivery) become three independent tab stacks without any imperative navigator configuration. The component layer supplies twelve presentational primitives — buttons, inputs, chips, status pills, skeletons, toasts and a custom tab bar — all of which read their colours, radii and shadows from a single design-token module, so a change to the brand palette propagates through every screen at once.

The state layer comprises two React Context providers mounted at the root. AuthProvider owns the authenticated user and the selected role and exposes setRole, signOut and refreshUser; CartProvider owns the cart array and derives cartTotal and cartCount from it. Both hydrate from device storage on mount and write back on change, which is why a cart survives an application restart.

The service layer is a single class, SupabaseService, exposing thirty static operations grouped into authentication, users, farmers, products, orders, reviews and file upload. Every method begins with the same guard: if the environment supplies a Supabase URL the method issues a PostgREST query and maps the snake_case row into a camelCase domain object; if it does not, the method delegates to localStore. Neither branch leaks into the caller.

The persistence layer therefore has two interchangeable implementations. The remote implementation is a hosted Supabase project providing PostgreSQL storage, GoTrue authentication and object storage. The local implementation is an in-memory state object holding the catalogue, farmer profiles and order history, mirrored into AsyncStorage after every mutation and rehydrated — including date revival — on the next launch.

2.1.3 Component Interaction

Order placement is the interaction that touches the greatest number of components, and it is worth tracing in full. When the customer presses Place Order, the payment screen validates the cart total against the minimum order value and the address against the pincode pattern, groups the cart lines by farmerId, and issues one createOrder call per distinct farmer in parallel. The service façade routes each call to the active persistence target, which assigns an identifier, appends the initial placed status entry and decrements the stock of each ordered product. Only when every promise resolves is the cart cleared and the customer redirected to the order history. Figure 2.4 shows the sequence.

2.1.4 Data Model

The domain is expressed as TypeScript interfaces in src/types/index.ts and mirrors the relational schema used when Supabase is the active target. User is the base identity; Customer, Farmer and DeliveryPartner extend it with a discriminated role literal, which lets the compiler narrow a value to the correct specialisation from the role field alone. Orders embed their line items and their status history as nested structures rather than referencing separate tables, so that an order is retrievable in a single read and its history cannot drift from the order it describes.

2.3.1 Authentication and Role Assignment Module

A new user opens the application and is redirected to the login screen by the root guard. The sign-up form collects a name, an email, a ten-digit Indian mobile number and a password; each is validated client-side before any network call is attempted. On successful registration the user is deliberately signed out again and returned to the sign-in tab, so that the session that eventually drives the application is always a genuine sign-in session rather than an artefact of registration.

On sign-in, the service returns a user record. If that record already carries a role, the user is routed directly to the corresponding workspace. If it does not, the user is sent to the role selection screen, where choosing Farmer additionally provisions a farmer profile with a derived farm name and a pending verification status. The chosen role is written both to the user record and to device storage, so that a subsequent cold start restores the workspace without a round trip.

The guard in app/_layout.tsx re-evaluates on every navigation segment change and enforces three rules: an unauthenticated user with no stored role is sent to login; an authenticated user without a role is sent to role selection; and a user with a role who is found anywhere outside their own route group is redirected to that group's landing screen. The guard deliberately early-returns while the user is on the role selection screen, which prevents the redirect loop that would otherwise occur during the brief window in which a user exists but a role does not.

2.3.2 Customer Module

The customer home screen loads the available catalogue and the verified farmer list in parallel. Products are presented as a two-column card grid; each card shows the category glyph, an organic badge where applicable, the farmer's name, the unit price and a one-tap add control. Above the grid the customer can search by name or description, filter by any of the eight categories, restrict the list to organic produce, and sort by ascending or descending price. Filtering by category re-queries the data source; search, organic filtering and sorting are applied client-side to the loaded set, which keeps typing responsive.

Selecting a card opens the product detail screen, which adds the harvest provenance, a stock badge that switches to an out-of-stock state at zero, a quantity stepper clamped to available stock and a farmer attribution card. Adding to the cart from either surface writes through CartContext, which merges quantities for a product already in the cart and caps the merged quantity at the product's stock.

The cart screen renders each line with a stepper and a remove control, and adds a progress indicator toward the free-delivery threshold that switches to a celebratory state once the threshold is crossed. The bill summary computes subtotal, delivery fee — zero above the threshold — and total. Checkout is blocked below the minimum order value, with the shortfall stated explicitly in the error message.

The checkout screen collects a delivery address, validates the pincode against the Indian six-digit pattern, offers cash on delivery, UPI and card, and then places the order. Because a cart may contain produce from several farmers, the cart is partitioned by farmer and one order is created per farmer, each with its own subtotal and its own fulfilment lifecycle. Payment status is recorded as pending for cash on delivery and paid for the two prepaid methods.

Order history lists all of the customer's orders newest first, filterable by all, active, delivered or cancelled. Each entry opens a tracking screen that renders the seven-stage timeline with completed stages marked, the current stage annotated in progress, an estimated delivery time derived from the order timestamp, the itemised bill, the delivery address and — while the order is still in placed or confirmed — a cancellation control.

2.3.3 Farmer Module

The farmer dashboard aggregates the farmer's orders and products into four indicators: active orders, active products, lifetime order count and realised earnings, the last computed as the sum of the totals of delivered orders only. Beneath the indicators, any product whose stock has fallen to or below the low-stock threshold is surfaced in an amber alert list with a direct link to inventory, followed by the five most recent orders with their status pills.

The products screen is the farmer's inventory console. It lists every product the farmer owns — including those currently hidden from customers, so that they can be restored — with search across name and category, a low-stock marker and an availability switch that toggles catalogue visibility without deleting the record. A modal sheet creates a new product, collecting name, description, category, unit, price, stock and an organic flag, with name, price and stock enforced as mandatory.

The orders screen is the fulfilment queue, filterable by active, all or completed. The farmer's authority over an order is deliberately bounded: the transition map allows only placed → confirmed and confirmed → packed. Once an order is packed it leaves the farmer's control and becomes visible to delivery partners. Every transition is confirmed through a dialogue before it is committed.

2.3.4 Delivery Module

The delivery partner's job board opens with an online/offline switch and two live counters for active deliveries and the fee accrued against them. When online, the partner sees every packed order that has not yet been claimed, each showing the drop address and — where the address carries coordinates — a straight-line distance and an estimated duration. Declining a job hides it locally for the remainder of the session; accepting it atomically sets the order status to assigned and stamps the partner's identifier onto the order, which removes it from every other partner's board.

Claimed orders move into My Deliveries, where a single contextual action advances the order along the remainder of the lifecycle: Pick Up at assigned, Start Delivery at picked up, and Delivered at out for delivery. Marking an order delivered also flips its payment status to paid, which closes the cash-on-delivery loop.

The route screen resolves the partner's single in-flight delivery and presents it as a pickup-to-drop schematic with the farm as origin and the customer address as destination, together with the order value and the same contextual advance action. The earnings screen aggregates all delivered orders into today, week-to-date and month-to-date totals at the standard per-delivery fee, and lists the ten most recent completed deliveries with relative timestamps.

2.4 Key Algorithms and Logic

Six pieces of logic carry most of the system's behaviour. Each is presented below as pseudocode followed by the reasoning behind it and, where instructive, the actual implementation.

2.4.1 Role-Based Navigation Guard

The guard is the single point at which authorisation is decided. Because Expo Router exposes the current URL as a segment array, the guard can compare the user's role against the segment they are attempting to occupy without any per-screen checks.

ALGORITHM  EnforceRouteAccess
INPUT      user, role, segments        // segments[0] is the active route group
OUTPUT     a redirect, or no action

1  IF authentication is still loading THEN return
2  group ← segments[0]
3  IF group = 'role-select' THEN return                  // avoid redirect loop
4  IF role is set AND group = groupFor(role) THEN return // already correct
5  IF user is null AND role is null AND group ≠ '(auth)' THEN
6      redirect '/(auth)/login'
7  ELSE IF (user OR role) AND role is null THEN
8      redirect '/role-select'
9  ELSE IF role is set THEN
10     IF group ≠ groupFor(role) OR group ∈ {'(auth)','role-select'} THEN
11         redirect landingFor(role)
       // groupFor : customer→(customer), farmer→(farmer), delivery→(delivery)
       // landingFor: customer→/home, farmer→/dashboard, delivery→/orders

Listing 2.1 — Route access enforcement (app/_layout.tsx).

Line 3 is the non-obvious one. During role assignment there is a window in which a user exists but a role does not; without the early return, rule 7 would fire on every render and pin the user to the role selection screen while the assignment was still in flight. Line 4 short-circuits the common case so that ordinary tab navigation inside a workspace performs no redirect work at all.

2.4.2 Order Lifecycle State Machine

An order occupies one of eight states. Seven of them form a strictly linear progression; cancelled is a terminal state reachable only from the two earliest states. What makes the machine safe is that no single role can drive an order from end to end: authority is partitioned, so a farmer cannot mark an order delivered and a delivery partner cannot confirm one.

ALGORITHM  AdvanceOrderStatus
INPUT      orderId, nextStatus, actorRole, note?
OUTPUT     persisted order with an appended history entry

1  order ← fetch(orderId)
2  IF order is null THEN return
3  allowed ← transitionsPermittedFor(actorRole, order.orderStatus)
4  IF nextStatus ∉ allowed THEN reject
5  order.orderStatus  ← nextStatus
6  order.statusHistory ← order.statusHistory + { nextStatus, now(), note }
7  IF nextStatus = 'delivered' THEN order.paymentStatus ← 'paid'
8  order.updatedAt ← now()
9  persist(order)

   transitionsPermittedFor(role, current):
     farmer   : placed→confirmed, confirmed→packed
     delivery : packed→assigned, assigned→picked_up,
                picked_up→out_for_delivery, out_for_delivery→delivered
     customer : placed→cancelled, confirmed→cancelled

Listing 2.2 — Guarded status transition with history append.

The history is append-only. Because each entry carries its own timestamp, the tracking timeline can be rendered purely from history without inferring times, and an audit of how long an order spent in each stage remains possible after the fact. In the implementation each role's screen owns its own transition table — nextStatusMap on the farmer's order queue and statusMap on the delivery job board — which is what enforces line 4 in practice.

2.4.3 Cart Quantity Reconciliation and Stock Capping

The cart must never promise more of a product than exists. Two entry points can violate that — adding a product already present, and typing a quantity directly — so the cap is applied inside the reducer rather than at either call site.

ALGORITHM  AddToCart
INPUT      product, quantity
OUTPUT     next cart state

1  cap(q) ← IF product.stock > 0 THEN min(q, product.stock) ELSE q
2  existing ← cart.find(line ⇒ line.productId = product.id)
3  IF existing exists THEN
4      RETURN cart with existing.quantity replaced by cap(existing.quantity + quantity)
5  ELSE
6      RETURN cart + { productId, product, quantity: cap(quantity), farmerId }

ALGORITHM  UpdateQuantity(productId, q)
1  IF q ≤ 0 THEN RETURN RemoveFromCart(productId)
2  maxStock ← line.product.stock > 0 ? line.product.stock : q
3  line.quantity ← min(q, maxStock)

Listing 2.3 — Cart reconciliation with stock capping (CartContext.tsx).

Persistence introduces a subtler hazard. The cart hydrates from storage asynchronously, while the effect that writes the cart back fires on the very first render — when the cart is still the empty initial state. Writing at that moment would erase the stored cart before it had been read. The implementation guards the write with a hydration flag that is only raised once the initial read has settled:

2.4.4 Order Splitting, Pricing and Fee Rules

A cart is a customer-side concept; an order is a farmer-side concept. Since one farmer cannot fulfil another's produce, a mixed cart must become several orders. The delivery fee, however, is charged once against the cart as a whole and is waived entirely above the free-delivery threshold.

ALGORITHM  PlaceOrder
INPUT      cart, address, paymentMethod, user
OUTPUT     one persisted order per distinct farmer

1  IF user is null              THEN prompt sign-in;      abort
2  IF cart is empty             THEN report;              abort
3  IF cartTotal < MIN_ORDER_VALUE THEN report shortfall;  abort
4  IF any address field is blank THEN report;             abort
5  IF NOT matches(address.pincode, /^[1-9][0-9]{5}$/) THEN report; abort
6  deliveryFee ← cartTotal ≥ FREE_DELIVERY_THRESHOLD ? 0 : DELIVERY_FEE
7  groups ← groupBy(cart, line ⇒ line.farmerId)
8  FOR EACH (farmerId, lines) IN groups IN PARALLEL
9      subtotal ← Σ line.product.pricePerUnit × line.quantity
10     createOrder({ orderNumber: unique(), customerId, farmerId,
                     items: map(lines), subtotal, deliveryFee,
                     total: subtotal + deliveryFee, deliveryAddress: address,
                     paymentMethod,
                     paymentStatus: paymentMethod = 'cod' ? 'pending' : 'paid',
                     orderStatus: 'placed',
                     statusHistory: [{ status:'placed', timestamp: now() }] })
11 AWAIT all
12 clearCart(); redirect to order history

2.4.5 Distance and Estimated Time of Arrival

The delivery job board ranks and annotates jobs by how far away the drop address is. Distance is computed with the Haversine formula over the great-circle path, using the partner's origin (a fixed reference point in the current build, since live location is out of scope) and the order's stored coordinates. The resulting distance is converted to a duration and floored at the baseline promise, so an ETA is never optimistic relative to the figure already shown to the customer.

ALGORITHM  DistanceAndETA
INPUT      (lat₁, lon₁) origin, (lat₂, lon₂) destination
OUTPUT     distance in km, estimated minutes

1  R ← 6371                                   // mean Earth radius, km
2  Δφ ← radians(lat₂ − lat₁);  Δλ ← radians(lon₂ − lon₁)
3  a  ← sin²(Δφ/2) + cos(radians(lat₁))·cos(radians(lat₂))·sin²(Δλ/2)
4  c  ← 2·atan2(√a, √(1−a))
5  d  ← R·c
6  IF d is not finite OR d ≤ 0 THEN RETURN (d, ESTIMATED_DELIVERY_MINUTES)
7  RETURN (d, max(ESTIMATED_DELIVERY_MINUTES, round(d × MINUTES_PER_KM)))

The on-device layer is not a stub that returns fixed arrays. It maintains genuine mutable state — creating an order decrements the stock of every product in it, advancing a status appends to that order's history, and adding a product makes it appear in the customer catalogue — and mirrors that state to AsyncStorage after every mutation.   return DATE_KEYS.has(key) && typeof value === 'string' ? new Date(value) : value;
}

3.1 Test Plan

3.1.1 Testing Strategy

The system under test is a client application whose correctness is dominated by two concerns: whether state changes made by one role become correctly visible to the others, and whether invalid input is refused before it reaches persistence. Neither concern is well served by unit tests of individual functions in isolation, because both are properties of a sequence of interactions across several screens. The strategy adopted therefore places its weight on automated end-to-end testing against the running application, supported by static verification.

Three complementary levels were applied:

  1. Static verification. The entire source tree is compiled with tsc --noEmit under strict. Because the domain model uses string-literal unions for roles, order statuses and product categories, a large class of defects — an unhandled status, a mistyped category, a nullable value dereferenced without a guard — is rejected at this level before any test is run.
  2. Functional end-to-end testing. The application is served on the web target and driven through a real Chrome instance over the DevTools Protocol. The suite, committed to the repository as tests/e2e/walkthrough.mjs, signs in as each of the three roles in turn and performs the complete business cycle: a customer places an order, the same order is confirmed and packed by the farmer, and the same order is then claimed and advanced by a delivery partner. This exercises cross-role propagation directly, because each role observes state written by the previous one.
  3. Validation and negative testing. A second committed suite, tests/e2e/validation.mjs, deliberately supplies invalid input at every guarded boundary — malformed credentials, an unselected role, a sub-minimum cart, a blank address, an invalid pincode, a product created with mandatory fields empty — and asserts that the application refuses the operation and reports the specific reason. This suite also verifies two stateful properties that are easy to regress: that the cart survives an application restart, and that navigating directly to another role's URL is redirected.

Both suites exit with a non-zero status when any case fails, so they can be wired into a continuous integration pipeline unchanged, and both are runnable by any reader of the repository with npm test once npm run web is serving the application.

Interaction with the application is performed through DOM-level event dispatch rather than synthetic mouse input at coordinates. This was a necessary adaptation: react-native-web routes presses through its own responder system, which does not consistently observe input synthesised by the DevTools Protocol on every screen. Dispatching the full pointer and mouse event chain to the nearest pressable ancestor of a located text node reproduces a genuine user press reliably. Controlled text inputs are driven through the underlying value setter followed by an input event, which is the mechanism React itself observes.

Five tables are required — users, farmers, products, orders and reviews — with column names in snake_case matching the mapping performed in the service layer, and a public uploads storage bucket. Chapter 6: Conclusion and Future Work

6.1 Summary of Implementation

This capstone delivered a working cross-platform mobile marketplace that removes the intermediaries between agricultural producers and the households that buy from them. The system is a single React Native codebase of forty-eight TypeScript source files — approximately 5,400 lines — organised into eighteen routed screens, twelve reusable interface components and a thirty-operation service façade, and it runs on Android, iOS and the web from that one source tree.

Three design decisions shaped the result more than any others. The first was to make the route group the unit of authorisation: because Expo Router derives navigation from the directory layout, each role's screens live in a physically separate directory and a single guard in the root layout is sufficient to enforce the boundary between them, with no per-screen permission checks anywhere in the codebase. The second was to partition authority over the order lifecycle across roles rather than concentrate it: a farmer may only advance an order to packed and a delivery partner may only take it from there, which makes an illegal transition unrepresentable in the interface rather than merely discouraged. The third was to put a façade in front of persistence, so that a single configuration flag chooses between a hosted Supabase backend and a on-device data layer without a line of screen code changing — the decision that lets the application keep working whether or not the network does.

The build was validated rather than merely exercised. The whole tree compiles cleanly under strict TypeScript, and forty automated test cases — twenty-five functional, fifteen validation — are committed to the repository under tests/e2e/ and execute against the running application through a real browser; all forty pass. The functional suite is a genuine integration test: one order was carried from a customer's cart, through a farmer's fulfilment queue, into a delivery partner's job board and on to pickup, with each role independently observing the state the previous role had written.

6.3 Limitations

The following limitations are stated deliberately, because a report that omits them is less useful than one that records them.

  • Payment is recorded, not processed. Selecting UPI or card marks the order paid without any gateway interaction. No money moves, and there is no settlement, refund or reconciliation path.
  • The on-device layer is single-tenant. When no cloud backend is configured, the local store deliberately ignores user identifiers so that one device can act as all three roles against shared data. Multi-user isolation depends entirely on enabling Supabase with Row Level Security.
  • The Supabase branch is statically verified but not executed. The remote half of each service method is type-checked but was not exercised at run time during testing, so its query construction and column mapping remain unproven against a live database.
  • Location is fixed, not sensed. Distance and ETA are computed correctly, but from a constant origin rather than the partner's device location, and the route screen is a schematic rather than a map.
  • Coverage is integration-level only. The committed suites drive the whole application, but there is no unit test runner, so pure helpers are covered only indirectly through the interfaces that call them.
  • Product imagery is absent. Products render a category glyph; the upload path exists in the service layer but no capture flow is wired to it.
  • Reviews and subscriptions are partial. Reviews have a data model and service methods but no authoring screen; subscriptions exist only as type definitions.
  • Notifications are absent. A customer learns that an order advanced only by opening the tracking screen, and a delivery partner learns of a new job only by refreshing the board.
  • Farmer verification is nominal. The status field exists and defaults to pending, but no document review workflow or administrative role has been implemented.

6.5 Concluding Remarks

The project set out to test a straightforward proposition: that the coordination barrier which keeps farmers and households apart is a software problem, and that removing it requires one application carrying all three participants rather than three separate ones. The delivered system supports that proposition. An order created by a customer is confirmed by the farmer who grew the produce and delivered by a partner who is paid for that specific journey, with no other party in the transaction and every state change visible to everyone who needs it. What remains before real use is largely integration work — payments, notifications, live location — rather than redesign, and the architecture described in Chapter 2 was chosen specifically so that each of those can be added behind interfaces that already exist.

Appendix A — User Manual

A.1 Getting Started

Open the application. If this is the first launch, the sign-in screen is presented.

  1. Create an account. Press Sign Up, then enter your full name, email address, ten-digit mobile number and a password of at least six characters. Press Create Account. You are returned to the sign-in tab with a confirmation.
  2. Sign in. Enter the same email address and password and press Sign In.
  3. Choose your role. Select Customer, Farmer or Delivery Partner and press Continue. The choice is remembered, so subsequent launches go straight to your workspace. To use a different role, sign out from the Profile tab and register a separate account.
Working offline. The application keeps its data on the device, so every screen continues to work without a network connection. When no cloud backend has been configured, any email address with a password of six or more characters will sign you in.

A.2 For Customers

Finding produce

  • The Home tab lists available produce. Type in the search field to match by name or description.
  • Tap a category chip — Vegetables, Fruits, Dairy, Grains, Herbs, Eggs, Honey, Other — to narrow the list; tap All to clear it.
  • Use the Sort & Filter row to show only organic produce or to order by price ascending or descending.
  • Tap any product card to open its detail screen, which shows the price per unit, remaining stock, whether it is certified organic and who grew it.

Building an order

  • Tap the green + on a card to add one unit, or open the product and use the stepper to choose a quantity before adding. Quantities are capped at available stock.
  • Open the Cart tab to review the order. Adjust quantities with the steppers, remove a line with ×, or clear everything with Clear.
  • The progress bar at the top shows how much more you need to add to qualify for free delivery (₹500). Below that threshold a ₹30 delivery fee applies. Orders below ₹100 cannot be placed.

Checkout and tracking

  • Press Proceed to Payment, choose Cash on Delivery, UPI or Card, and enter your delivery address. The pincode must be a valid six-digit Indian code.
  • Press Place Order. If your cart contains produce from more than one farm, a separate order is created for each — this is expected, since each farm fulfils its own items.
  • Open the Orders tab to see your history, filtered by All, Active, Delivered or Cancelled. Press Track Order on any entry to follow its seven stages and see the estimated delivery time.
  • An order may be cancelled from the tracking screen while it is still Order Placed or Confirmed. Once the farmer has packed it, cancellation is no longer offered.

A.3 For Farmers

  • The Home tab summarises your business: active orders, active products, lifetime orders and earnings from delivered orders. Any produce at or below ten units appears in an amber Low Stock list — press Restock to jump to inventory.
  • The Products tab lists everything you sell. Use the switch on each row to hide a product from customers without deleting it, and the search field to find a product by name or category.
  • Press + Add to publish new produce. Name, price and stock are required; description, category, unit and the organic flag are optional. Press Add Product to save.
  • The Orders tab is your fulfilment queue. Filter by Active, All or Completed. For each new order press Mark Confirmed, then Mark Packed once it is ready for collection. After packing, the order becomes visible to delivery partners and leaves your queue.

A.4 For Delivery Partners

  • Use the Online / Offline switch at the top of the Orders tab to control whether you receive jobs. While offline the available list is empty.
  • Available Orders shows packed orders no one has claimed, each with the drop address, approximate distance and estimated duration, and the ₹30 fee. Press Accept to claim a job or Decline to hide it for this session.
  • Claimed jobs appear under My Deliveries. Advance each one in order: Pick Up when you have collected from the farm, Start Delivery when you set off, and Delivered on handover.
  • The Map tab shows the pickup and drop details for your current delivery and offers the same advance action.
  • The Earnings tab shows your total, with today, this week and this month breakdowns and your ten most recent completed deliveries.

B.3 Optional — Connecting a Supabase Backend

  1. Create a project at supabase.com and copy its project URL and anonymous key.
  2. Copy the template and fill it in: 
    cp .env.example .env

EXPO_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
EXPO_PUBLIC_SUPABASE_ANON_KEY=<anon-key>
  3. Create the tables users, farmers, products, orders and reviews with snake_case columns matching the mapping in src/services/supabase.ts, and a public storage bucket named uploads.
  4. Enable Row Level Security on every table and add policies granting each user access only to their own records, farmers control of their own products, all authenticated users read access to available products, and delivery partners read access to orders assigned to them or awaiting assignment.
  5. Stop and restart Metro. The application now uses the remote backend; nothing in the source changes.

B.5 Troubleshooting

Metro fails to start, or the bundle is staleClear the cache: npx expo start -c.
Expo Go cannot reach the development serverEnsure the handset and the host are on the same network, or start with npx expo start --tunnel.

Dependency version warnings on start-upAlign packages with the installed SDK: npx expo install --fix.
On-device data has drifted during testingClear application storage — on the web, clear the site's local storage; on a device, clear the Expo Go app data — and relaunch to restore the defaults.
